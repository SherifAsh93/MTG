01 · Purpose, ownership and workflow  Contigoo Studio is your internal development workspace and management system. You build, operate and maintain your work here. Clients do not log in to Studio.  Private owner notes · 22 September 2026 · Version 1.1. These notes supersede earlier descriptions of client administrators or client users accessing this project.  Who owns and uses the system  You:   the only Super Admin and the only creator/developer of the platform and its applications.  Employees:   internal users you will add after completing the system, with management permissions you explicitly assign.  Clients:   people/organizations recorded and managed inside Studio. A client record is not a user account and creates no login access.  Client-facing delivery:   access to any separately delivered application or website must be scoped separately; it is not client access to this internal Studio.  Development and management together  Area   Purpose  Overview   Actual saved clients, projects, pending changes, archived work and activity.  Clients   Create, view, update and delete client details; manage their related projects.  Projects & solutions  One place to create projects, find existing work and manage its lifecycle.  Manage project   App usage, records, project details, prices, publications, archive/reactivate and deletion.  Open in Studio   Your visual development workspace: apps, data, pages, workflows, branding, preview and publishing.  App library   Reusable capabilities and custom-app templates, used within an explicitly selected project.  One creation path:   Projects & solutions   →   Create project   →   client and project details   →   blank or optional framework   →   Open Studio. Framework starters belong inside setup, not in a competing starting page.  Ongoing work:   return to Manage, use the configured apps, review changes and quotes, reopen Studio for development, publish an update, then continue maintaining the project. One client can have several independent projects.  New workspaces start empty. Earlier names such as “Noura Restaurant” were fictional examples. Existing saved work is preserved until you explicitly edit or delete it. CRM, Inventory, Finance, HR and Commerce remain capability choices, not a requirement to build the entire catalog at once. Authentication and authorization  Authentication   establishes who signed in.   Authorization   controls which clients, projects, records and actions that internal user may access. Both belong in the backend foundation, even though employees are added later.  Account   Initial authority  Sole Super Admin / developer  Platform administration, development, catalog changes, security, employee provisioning and publication.  Employee   Only the management functions and client/project records assigned by the owner. No automatic development, publication or administrator authority.  Employee grants remain to be defined. Login implementation requirements  Resolve the three identifiers to the same immutable user ID; prevent duplicate or ambiguous username/email/phone matches. Keep password verification in the identity service using salted password hashing. Bootstrap the owner through protected setup, never a hardcoded or documented password.  Use secure server-managed sessions, rate-limited login and recovery, and audited access changes. Employee suspension must revoke access; employee APIs cannot create a second Super Admin. 03 · Infrastructure and database  Today:   HTML/CSS/JavaScript, a local Node static server, and browser localStorage. GitHub Pages hosts the updated v0.5 presentation; Vercel is an optional host for the same source. There is no real API, database or authentication yet. Hosting files on a VPS alone does not add those services.  Working production baseline  The architecture direction is accepted in principle. Exact versions, sizing and deployment configuration depend on the VPS inventory and implementation validation.  Component   Technology and responsibility  Internal web application  Next.js + TypeScript: management screens and the protected Studio editor.  API / application runtime  NestJS modular monolith: validation, employee permissions, data access, business modules and publication.  Business database   PostgreSQL: clients, projects, records, configurations, prices, versions and audit history.  Identity service   Keycloak / OpenID Connect: owner and employee identities, credentials, sessions and recovery; validate the phone-login extension.  Background work   Redis + worker for email, imports and scheduled workflows as implemented.  Uploaded files   VPS-managed persistent file/object storage for logos, documents and media, with authorized access.  HTTPS and deployment  Caddy routing/TLS plus Docker Compose on the approved VPS; respect any existing hosting services.  Delivery and recovery  Version-controlled builds/migrations, logs/health monitoring and encrypted off-VPS backups with restore tests.  Request path:   Internal browser   →   HTTPS   →   Web application   →   API   →   PostgreSQL. The identity service performs login; the API enforces current permissions on every operation.  What the database contains  Clients and projects:   commercial records and related work, separated from internal user accounts.  Staff access:   user profiles linked to identity-provider IDs, employee roles, permissions and client/project assignments. The owner is a single designated account.  Studio metadata:   validated definitions for entities, fields, pages, workflows, bindings and installed modules. Use versioned metadata/JSONB where appropriate.  Business data and quotes:   module-owned records, files, integer-money prices and quote snapshots. Critical domain rules use database constraints and transactions.  Versions and audit:   retained configuration publications and accountable changes. Configuration snapshots are not backups of business records.  One internal organization: scope records by client/project and employee assignments, without customer login. PostgreSQL row-level security can reinforce access. Keycloak has a separate database/account on the same PostgreSQL server. Browsers never connect directly to the database. 04 · Hosting, delivery and acceptance  Target:   the entire internal system runs on your VPS and subdomain, using your resources. GitHub Pages/Vercel are temporary presentation hosts, not required runtime services. Initially only you use it; employees join after completion. Build access controls from the beginning.  Implementation order  1.   Confirm the environment:   VPS OS/resources, existing services, domain, repository and Codex/direct implementation workflow.  2.   Build the protected foundation:   PostgreSQL schema/migrations, owner bootstrap, username/email/phone login, sessions, server permissions and auditing.  3.   Implement management:   Clients and Projects CRUD, lifecycle, pricing, assigned-record access and employee administration restricted to you.  4.   Connect Studio and runtime:   visual metadata, reusable apps, forms/records/workflows, preview, versioned publication and upgrade behavior.  5.   Deploy and validate:   HTTPS, persistence, logging, backups/restores and access tests on the authorized VPS environment.  6.   Onboard employees after completion:   create internal users, assign the minimum required management permissions, test their access and operate the system.  Operations to plan  A single VPS can run the initial service set using persistent volumes. A small-pilot planning estimate is approximately 4 vCPU, 8 GB RAM and 80+ GB SSD, subject to real workload and other hosted applications. This is not a capacity guarantee or a high-availability design.  Back up database/files off the VPS and test restoration. Monitor health, errors and disk usage. Keep secrets outside source. Plan migrations, rollback and employee offboarding. Keep portable builds and self-hostable services; browser-local demo data needs explicit transfer when changing domains.  Acceptance checks — planned, not passed  N1 — Owner:   exactly one designated Super Admin/developer; employees cannot elevate themselves or create another owner.  N2 — Login:   username, verified email and normalized/verified phone authenticate the same account with its password; invalid and ambiguous identifiers are rejected.  N3 — Employee access:   assigned operations succeed; unassigned clients/projects, development tools and privileged actions are denied by the API.  N4 — Internal boundary:   client creation grants no Studio access; no client registration/login or customer- admin role is introduced.  N5 — Lifecycle:   create, edit, use, publish, update, archive/reactivate and delete work with preserved versions and explicit data handling.  N6 — VPS operation:   HTTPS login, persistent storage, employee suspension/session revocation, audit evidence and an off-VPS backup restore succeed.  Still needed:   VPS specification/current services, domain, repository/workflow, phone country and verification/recovery method, and employee permission definitions. Existing prototype checks validate local behavior only; no production login or VPS acceptance test has run.

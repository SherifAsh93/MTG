01 · Product mandate and release boundaries  Confirmed direction  Build a completely new Contigoo website and business platform with CRM, Sales, Finance, Inventory, HR, and broader ERP capabilities. Customers can subscribe to individual apps or a complete-platform offering. Each app must be useful on its own and connected when purchased together. The meaning of a one-time purchase, source-code access, and customer-hosted installation remains open.  Customers need branding and configuration controls. Contigoo's administrator needs broad platform configuration capabilities. Authentication, authorization, and security rules are fundamental. Codex on the owner's VPS is the preferred implementation tool.  Proposed first commercial release  A reliable   CRM-led SaaS pilot   for one narrowly chosen customer segment: business workspace provisioning, membership, role-based access, accounts/contacts/leads/opportunities, activities, configurable fields/forms/views, basic reporting, one bounded workflow engine, app entitlements, billing integration, audit history, and operational recovery.  The public website covers product pages, approved packages, signup, authentication entry, onboarding, and customer account management. The authenticated platform has an app launcher, shared navigation, customer administration, and a separate Contigoo administration surface.  First-release boundaries  Defer a general-purpose app builder, arbitrary customer code, public marketplace, complex territory hierarchies, offline synchronization, enterprise consolidation, manufacturing, advanced warehouse management, and statutory payroll. Add a capability when its customer workflow, owner, dependencies, and acceptance criteria are defined.  What “finished” means  The pilot is finished when its chosen end-to-end workflows work, all applicable release-blocking tests pass, operational recovery is demonstrated, documentation exists, and named pilot users accept it. The full product evolves through separately accepted module releases; “complete ERP” is not a sufficiently bounded endpoint.  Owner accountability:   product decisions, architecture review, domain correctness, acceptance, and deployment decisions.   Codex accountability:   bounded implementations, tests, migration scripts, and accurate handoff evidence under the owner's review. 03 · Product packaging and app independence  Separate four concepts  Deployment   says where software runs.   Subscription/license   says what the customer bought.   Entitlement  says what capabilities are enabled now.   Authorization   says which users can perform which operations. One does not replace the others.  Offer   Proposed behavior   Decision still needed  Single app   Includes core identity/workspace services and that app's usable workflow  Seat/usage limits and support tier  Selected bundle   Union of enabled app capabilities with explicit dependencies  Discounts and billing changes  Complete-platform subscription  A versioned package listing included apps   Whether future apps are included  One-time purchase   A separate license product, if offered   Updates, hosting, support, term, source-code rights  Dedicated installation   A separately operated copy, if offered   Upgrade service, isolation, capacity, support price  Module contract  Each module publishes a manifest with an immutable key, version, core compatibility, core dependencies, optional integrations, permissions, navigation, migrations, events, and entitlements. Apps may depend on shared platform primitives; paid-app dependencies must be explicit in the catalog before sale.  Core owns reusable parties/contacts and reference data; CRM owns its lead and opportunity lifecycle. Inventory can use parties and products without requiring the CRM app. Finance can consume approved business documents without directly updating another module's tables.  Entitlement lifecycle  Maintain internal subscription and entitlement records. Verify provider webhook signatures, store event identifiers, reconcile provider state, and apply updates idempotently. Never grant access from the checkout return URL alone. Deny unknown states by default.  Proposed policy, requiring D08 approval:   trial and active accounts receive their purchased capabilities; past- due accounts get a configurable grace interval; after grace, ordinary writes stop while permitted read/export access remains for a defined retention window. Cancellation at period end preserves access until the paid- through date. No automatic destructive data deletion on cancellation.  Enforce entitlements in API requests, background jobs, exports, integrations, and workflow execution. Downgrades must flag incompatible configurations and preserve data. Quotas need atomic checks, not a UI- only counter. Log and reconcile grants, revocations, and administrative overrides. 06 · Data ownership and tenancy model  Core model  Area   Representative records   Ownership and constraints  Identity   User, external identity   External subject maps to a local user; tenant membership is separate  Customer   Tenant, membership, team, role, policy   A user may belong to multiple tenants; each request selects a verified one  Commerci al  Plan version, subscription, entitlement, usage  Internal state reconciles with provider events  Shared data  Party, contact point, address, currency, product  App-neutral primitives with controlled exposure  Configurati on  Entity/field definitions, form, view, workflow version  Published versions are immutable; drafts are isolated  Operations   Audit event, outbox event, job receipt, file reference  Tenant and actor tracked; sensitive values redacted  Business ownership  CRM owns leads, opportunities, pipelines, activities, and conversion links. Sales later owns quotes and orders. Inventory owns stock movements/reservations and warehouse state. Finance owns journals and posting state. HR owns employee records and leave; a shared contact is not permission to view employee data.  Mandatory invariants  Every tenant-owned row carries an immutable   tenant_id   ; global tables are explicitly enumerated.  Use tenant-aware unique constraints and composite foreign keys where needed to prevent cross-tenant relationships.  API runtime role must not own protected tables or have   BYPASSRLS   . Evaluate   FORCE ROW LEVEL SECURITY   ; migration roles are separate.  Set tenant context transaction-locally from verified server state. Never trust a submitted tenant ID without a membership check. Missing context must fail closed.  Test the actual connection pool for context leakage after commit, rollback, exceptions, and reuse.  Use fixed-precision decimal arithmetic for money and quantity; record currency and rounding policy. Store instants consistently in UTC and preserve relevant business timezone/date semantics.  Protect concurrency with transactions, locks or optimistic versions. Idempotency keys include tenant, operation, and payload consistency.  Custom data and deletion  Use typed core columns for invariant business data and validated custom-field storage for extension data. JSONB is a candidate for custom values; bound queries and add indexes based on measured usage. Do not implement the whole business model as an untyped entity-attribute-value store.  Define archive, retention, export, and deletion separately. Accounting postings and audit records need controlled correction/retention rules rather than ordinary delete buttons. Validate backup and privacy policies against the selected market before launch. 07 · Security and administrator model  Access decision  An operation is allowed only if   identity + active membership + tenant scope + app entitlement + action permission + record scope + field policy   all pass. Apply the same evaluator to the API, reports, exports, integrations, and workers.  Principal   Intended authority  Contigoo platform operator  Catalog/configuration, tenant operations and service health; business-data access only through explicit support procedures  Tenant owner/admin   Own workspace, users, purchased apps and permitted configuration  App manager   Assigned app configuration and team operations within tenant policy  End user   Permitted actions on permitted records and fields  Integration/service actor  Narrow, revocable scopes for one tenant and integration  Pilot security baseline  Use a proven identity provider; require MFA for privileged accounts, secure invitations, verified identity linking, short-lived sessions/tokens where appropriate, and explicit session revocation. Protect browser sessions with secure, HttpOnly cookies and CSRF controls where cookies authenticate mutations. Define CORS and rate limits; do not invent password cryptography.  Start with role/action permissions and own/team/all record scopes where required by the pilot. Add field-level read/write rules for sensitive fields. Prevent mass assignment: clients cannot set tenant ownership, roles, entitlement grants, posting state, or audit fields through generic update APIs.  Validate filter/sort expressions and parameterize database queries. Sanitize rich text and templates; apply Content Security Policy. Validate uploads by content/type/size, quarantine where needed, keep storage private, and authorize every file download. Treat outbound webhooks as an SSRF boundary with destination restrictions and controlled network access.  Administrative customization has limits  Neither customer customization nor Contigoo configuration should disable tenant isolation, hide required audit trails, or change posted financial invariants. Separate platform configuration authority from unrestricted database access. A support-access session is time-bounded, justified, scoped, visible to operators, and audited; impersonation must be clearly indicated if later implemented.  Verification and evidence  Use cross-tenant and low-privilege negative tests at API and database layers. Review access-changing code separately. Maintain dependency/secret scanning, sanitized logs, backup encryption, and a tested incident runbook. Resolve release-blocking findings before exposing real customer data. Map applicable controls against OWASP ASVS; do not claim certification based on this guide. 08 · Customization as a product capability  The differentiator must be demonstrated through useful customer tasks, not the statement “more dynamic than Dynamics 365.” Measure setup time, upgrade safety, configuration reuse, and how often customers need code changes.  Level   Customer/admin capability   Proposed delivery  1 — Brand   Logo, approved colors, company details, locale   Pilot  2 — Workspace  App navigation, labels, preferences, saved views   Pilot  3 — Data/UI   Typed custom fields, forms, sections, validation, dashboards  Bounded pilot scope  4 — Process   Triggers, conditions, approved actions, approvals   Small action set in pilot; expand later  5 — Extension   Custom entities, integration packages, custom apps   Separate later release  Configuration lifecycle  Platform defaults   →   module defaults   →   tenant overlay   →   user preferences. Explicitly define which properties may be overridden and which layer wins. Keep stable internal keys even if visible labels change.  Every published configuration has a version, dependency list, author, timestamp, validation result, and rollback target. Use   draft   →   validate   →   preview   →   publish . Publishing switches atomically; in-flight workflows keep a defined version. Distinguish rolling back presentation metadata from reversing a data migration, which may not be safe.  Pilot field types and constraints  Start with text, number/decimal, date, boolean, choice, and controlled lookup types. Define required/unique behavior, defaults, maximum lengths, search/export behavior, and field visibility. The server enforces the same schema as the renderer. Do not allow a new required field to silently invalidate existing records; require a backfill or explicit staged activation policy.  Upgrade-safe extension rules  Use namespaced immutable keys; archive instead of destructive removal when data or dependencies exist. Before publishing, identify referenced views, reports, workflows, and indexes. Preserve customer configuration during module upgrades and report conflicts instead of overwriting silently.  Do not accept raw SQL, arbitrary JavaScript, HTML scripts, or unlimited regular expressions from tenant settings. Use an allowlisted expression language with execution limits. Enforce quotas for fields, workflow depth, execution rate, and report complexity. Accessible contrast constraints still apply to customer-selected colors.  Pilot success demonstration:   a tenant admin changes branding, adds a field, alters a form, saves a view, and publishes a bounded workflow without developer intervention; another tenant remains unaffected. Each module needs its own domain review, acceptance scope, migration plan, and independent-sale test.  Module   First useful release   Critical invariants / prerequisites  Sales   Quotes, approved prices, discounts, orders   Currency/rounding, approval authority, immutable accepted terms; no duplicate fulfillment  Inventory   Products/SKUs, warehouses, receipts, issues, transfers, reservations  Atomic stock movements; explicit negative-stock and valuation policies; unit conversions  Finance   Chart of accounts, journals, receivables/payables, posting, period close, trial balance  Balanced entries; immutable posted journals; controlled reversals; supported jurisdiction  HR   Employee directory, organization structure, leave policy/requests  Sensitive field access, correct accrual and approval, retention rules  Procurem ent  Suppliers, requisitions, purchase orders, receiving  Approval limits; receipt/invoice reconciliation; segregation of duties  Helpdesk   Tickets, queues, ownership, SLA clocks, customer links  Customer visibility, timezone-aware SLA timing, auditability  Scope distinctions  Invoicing is not full accounting. 11 · Workflows, reporting and integrations  Bounded workflow engine  Pilot triggers: record created/updated and scheduled reminder. Pilot conditions: typed comparisons over authorized fields. Pilot actions: create task, notify user, assign owner, and controlled field update. Add approvals only after defining authority, delegation, rejection, timeout, and resubmission semantics.  Use versioned workflow definitions, tenant-specific quotas, run history, correlation IDs, retry limits, exponential backoff, dead-letter handling, and a manual replay policy. Prevent cycles and repeated self- triggering. Execute with an explicit user or service identity; re-check membership, permissions, and entitlements before sensitive side effects. Snapshotting a workflow version is not permission to retain revoked authority.  Reporting  Begin with saved filtered lists, pipeline aggregations, dashboard cards, and CSV exports. Reuse the permission evaluator and field policy. Aggregate data can also leak sensitive information; permitted rows and fields must be applied before aggregation.  Bound report complexity, date ranges, page sizes, and export size. Use background jobs for large exports, short-lived private downloads, expiry, and audit events. Include tenant/policy/configuration versions in cache keys or invalidate caches when they change.  Integration boundary  Publish a versioned REST API and documented webhook events. Give each integration a tenant-scoped revocable credential and minimal scopes. Define pagination, rate limits, idempotency, retry semantics, and event version compatibility. Do not expose generic database access.  Store inbound provider event identifiers before applying effects; verify signatures and replay rules. Outbound delivery is at-least-once; consumers must deduplicate. Keep credentials in a secret store and redact payload fields from logs where needed.  Failure behavior  An email outage should not roll back a valid lead save. Record the business transaction and outbox entry, then retry notification. A failed financial posting needs visible reconciliation and cannot be represented as a successfully completed posting. Distinguish accepted-for-processing from completed operations in the API and UI.  Build versus buy:   integrate commodity identity, payment processing, email, storage, and monitoring where economical. Own the tenant/module contracts, customization behavior, domain workflows, and user experience. Evaluate vendor export paths, regional support, costs, and failure modes in P0. 12 · VPS deployment and operational baseline  The VPS is available to the owner, but its OS, capacity, services, access, and topology have not been inspected. This guide does not authorize changes to that server. Begin with an inventory and a capacity baseline.  Proposed deployment path  Use a Linux container deployment if the VPS supports it: reverse proxy/TLS   →   web/API   →   worker   →  PostgreSQL/Redis, with private object storage and external providers. Keep database and Redis ports off the public internet. Separate development, staging, and production credentials/data. A staging stack on the same host is logically separate but does not provide independent failure isolation.  Start with Docker Compose or equivalent reproducible orchestration. Kubernetes is not required for the proposed pilot. Pin images, run processes as non-root where practical, set resource limits, rotate logs, and document restart behavior. Build images in CI rather than editing production containers.  Provisional service objectives  Measure   Initial target to validate  Typical CRUD API latency   p95   ≤   500 ms at 50 concurrent active virtual users  Representative data   At least 10 tenants and 100,000 CRM records total, including one larger tenant  Load test error rate   < 1% unexpected errors; zero isolation failures  Availability aspiration   99.5% monthly after measurement; not a contractual SLA  Recovery point / time   Proposed RPO   ≤   1 hour; RTO   ≤   4 hours; confirm budget and test  These targets are workload-specific, not VPS capacity claims.

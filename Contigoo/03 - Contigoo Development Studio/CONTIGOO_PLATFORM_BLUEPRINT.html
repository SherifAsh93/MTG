01 · Product mandate and release boundaries

Confirmed direction

Build a completely new Contigoo website and business platform with CRM, Sales, Finance, Inventory, HR, and broader ERP capabilities. Customers can subscribe to individual apps or a complete-platform offering. Each app must be useful on its own and connected when purchased together. The meaning of a one-time purchase, source-code access, and customer-hosted installation remains open.

Customers need branding and configuration controls. Contigoo's administrator needs broad platform configuration capabilities. Authentication, authorization, and security rules are fundamental. Codex in a local session on the owner's personal laptop is the preferred implementation tool (corrected 30 September 2026 — no VPS is used for Contigoo).

Proposed first commercial release

A reliable CRM-led SaaS pilot for one narrowly chosen customer segment: business workspace provisioning, membership, role-based access, accounts/contacts/leads/opportunities, activities, configurable fields/forms/views, basic reporting, one bounded workflow engine, app entitlements, billing integration, audit history, and operational recovery.

The public website covers product pages, approved packages, signup, authentication entry, onboarding, and customer account management. The authenticated platform has an app launcher, shared navigation, customer administration, and a separate Contigoo administration surface.

First-release boundaries

Defer a general-purpose app builder, arbitrary customer code, public marketplace, complex territory hierarchies, offline synchronization, enterprise consolidation, manufacturing, advanced warehouse management, and statutory payroll. Add a capability when its customer workflow, owner, dependencies, and acceptance criteria are defined.

What “finished” means

The pilot is finished when its chosen end-to-end workflows work, all applicable release-blocking tests pass, operational recovery is demonstrated, documentation exists, and named pilot users accept it. The full product evolves through separately accepted module releases; “complete ERP” is not a sufficiently bounded endpoint.

Owner accountability: product decisions, architecture review, domain correctness, acceptance, and deployment decisions. Codex accountability: bounded implementations, tests, migration scripts, and accurate handoff evidence under the owner's review.

02 · Executive notes: keep, refine, decide

Proposed architectural decisions

ADR-001 — Modular monolith. One API codebase and deployment family, strongly separated modules, plus a worker process. Avoid early distributed-service coordination. Revisit only when measured scaling, ownership, or deployment needs justify extraction.

ADR-002 — Shared tenant-aware database. PostgreSQL with tenant-scoped access and row-level security as defense in depth. Prove isolation with the actual runtime role, transaction boundaries, and pool configuration before adopting the data-access library.

ADR-003 — Controlled metadata. Stable system entities plus versioned customer fields and presentation rules. Preserve core constraints and forbid arbitrary executable customer scripts in the pilot.

ADR-004 — SaaS-first commercial pilot. Preserve module independence without promising separate customer deployments. Dedicated installations need a separate support, upgrade, licensing, and security model.

These are proposals to record as accepted/rejected/superseded during P0. They are not decisions already made by the owner.

03 · Product packaging and app independence

Separate four concepts

Deployment says where software runs. Subscription/license says what the customer bought. Entitlement says what capabilities are enabled now. Authorization says which users can perform which operations. One does not replace the others.

Offer Proposed behavior Decision still needed
Single app Includes core identity/workspace services and that app's usable workflow Seat/usage limits and support tier
Selected bundle Union of enabled app capabilities with explicit dependencies Discounts and billing changes
Complete-platform subscription A versioned package listing included apps Whether future apps are included
One-time purchase A separate license product, if offered Updates, hosting, support, term, source-code rights
Dedicated installation A separately operated copy, if offered Upgrade service, isolation, capacity, support price

Module contract

Each module publishes a manifest with an immutable key, version, core compatibility, core dependencies, optional integrations, permissions, navigation, migrations, events, and entitlements. Apps may depend on shared platform primitives; paid-app dependencies must be explicit in the catalog before sale.

Core owns reusable parties/contacts and reference data; CRM owns its lead and opportunity lifecycle. Inventory can use parties and products without requiring the CRM app. Finance can consume approved business documents without directly updating another module's tables.

Entitlement lifecycle

Maintain internal subscription and entitlement records. Verify provider webhook signatures, store event identifiers, reconcile provider state, and apply updates idempotently. Never grant access from the checkout return URL alone. Deny unknown states by default.

Proposed policy, requiring D08 approval: trial and active accounts receive their purchased capabilities; past-due accounts get a configurable grace interval; after grace, ordinary writes stop while permitted read/export access remains for a defined retention window. Cancellation at period end preserves access until the paid-through date. No automatic destructive data deletion on cancellation.

Enforce entitlements in API requests, background jobs, exports, integrations, and workflow execution. Downgrades must flag incompatible configurations and preserve data. Quotas need atomic checks, not a UI-only counter. Log and reconcile grants, revocations, and administrative overrides.

04 · Reference architecture

Proposed starting architecture: a modular monolith with a separately runnable worker and a shared database. Module independence is achieved through boundaries and contracts, not a separate service for every app.

EXPERIENCEPublic website · Customer workspace · Contigoo administration
↓ authenticated, validated requests ↓
PLATFORM COREIdentity adapter · Tenancy · Authorization · Entitlements · Audit
SHARED FRAMEWORKSMetadata · UI components · Workflow · Reporting · Files · Notifications
BUSINESS MODULESCRM / Sales · Inventory · Finance · HR · Procurement · Helpdesk
↓ scoped repositories / domain services / transactional outbox ↓
INFRASTRUCTUREPostgreSQL · Queue/cache · Worker · Object storage · OIDC · Billing

Request path

Validate session/token → resolve trusted tenant membership → check app entitlement → check action/record/field permissions → validate payload and metadata → execute transaction → persist audit/outbox records → return only authorized fields. Queued work repeats relevant checks under an explicit actor and tenant context.

Boundary rules

  1. No business module writes directly into another module's tables.
  2. Shared identity and party records have an explicit owning core service.
  3. Use synchronous internal service calls for immediate transactional operations; use domain events for eventual side effects.
  4. An outbox entry is committed with its source transaction. Consumers are retryable and deduplicate events. Do not claim exactly-once message delivery.
  5. Record identifiers, cache keys, file access, search, metrics labels, and jobs must respect tenant scope.
  6. Contigoo administrative access is separate from ordinary tenant roles, narrowly scoped, and audited.

Extract a service only after identifying the measured bottleneck, interface contract, failure model, operational owner, and migration strategy.

06 · Data ownership and tenancy model

Core model

Area Representative records Ownership and constraints
Identity User, external identity External subject maps to a local user; tenant membership is separate
Customer Tenant, membership, team, role, policy A user may belong to multiple tenants; each request selects a verified one
Commercial Plan version, subscription, entitlement, usage Internal state reconciles with provider events
Shared data Party, contact point, address, currency, product App-neutral primitives with controlled exposure
Configuration Entity/field definitions, form, view, workflow version Published versions are immutable; drafts are isolated
Operations Audit event, outbox event, job receipt, file reference Tenant and actor tracked; sensitive values redacted

Business ownership

CRM owns leads, opportunities, pipelines, activities, and conversion links. Sales later owns quotes and orders. Inventory owns stock movements/reservations and warehouse state. Finance owns journals and posting state. HR owns employee records and leave; a shared contact is not permission to view employee data.

Mandatory invariants

  • Every tenant-owned row carries an immutable tenant_id; global tables are explicitly enumerated.
  • Use tenant-aware unique constraints and composite foreign keys where needed to prevent cross-tenant relationships.
  • API runtime role must not own protected tables or have BYPASSRLS. Evaluate FORCE ROW LEVEL SECURITY; migration roles are separate.
  • Set tenant context transaction-locally from verified server state. Never trust a submitted tenant ID without a membership check. Missing context must fail closed.
  • Test the actual connection pool for context leakage after commit, rollback, exceptions, and reuse.
  • Use fixed-precision decimal arithmetic for money and quantity; record currency and rounding policy. Store instants consistently in UTC and preserve relevant business timezone/date semantics.
  • Protect concurrency with transactions, locks or optimistic versions. Idempotency keys include tenant, operation, and payload consistency.

Custom data and deletion

Use typed core columns for invariant business data and validated custom-field storage for extension data. JSONB is a candidate for custom values; bound queries and add indexes based on measured usage. Do not implement the whole business model as an untyped entity-attribute-value store.

Define archive, retention, export, and deletion separately. Accounting postings and audit records need controlled correction/retention rules rather than ordinary delete buttons. Validate backup and privacy policies against the selected market before launch.

07 · Security and administrator model

Access decision

An operation is allowed only if identity + active membership + tenant scope + app entitlement + action permission + record scope + field policy all pass. Apply the same evaluator to the API, reports, exports, integrations, and workers.

Principal Intended authority
Contigoo platform operator Catalog/configuration, tenant operations and service health; business-data access only through explicit support procedures
Tenant owner/admin Own workspace, users, purchased apps and permitted configuration
App manager Assigned app configuration and team operations within tenant policy
End user Permitted actions on permitted records and fields
Integration/service actor Narrow, revocable scopes for one tenant and integration

Pilot security baseline

Use a proven identity provider; require MFA for privileged accounts, secure invitations, verified identity linking, short-lived sessions/tokens where appropriate, and explicit session revocation. Protect browser sessions with secure, HttpOnly cookies and CSRF controls where cookies authenticate mutations. Define CORS and rate limits; do not invent password cryptography.

Start with role/action permissions and own/team/all record scopes where required by the pilot. Add field-level read/write rules for sensitive fields. Prevent mass assignment: clients cannot set tenant ownership, roles, entitlement grants, posting state, or audit fields through generic update APIs.

Validate filter/sort expressions and parameterize database queries. Sanitize rich text and templates; apply Content Security Policy. Validate uploads by content/type/size, quarantine where needed, keep storage private, and authorize every file download. Treat outbound webhooks as an SSRF boundary with destination restrictions and controlled network access.

Administrative customization has limits

Neither customer customization nor Contigoo configuration should disable tenant isolation, hide required audit trails, or change posted financial invariants. Separate platform configuration authority from unrestricted database access. A support-access session is time-bounded, justified, scoped, visible to operators, and audited; impersonation must be clearly indicated if later implemented.

Verification and evidence

Use cross-tenant and low-privilege negative tests at API and database layers. Review access-changing code separately. Maintain dependency/secret scanning, sanitized logs, backup encryption, and a tested incident runbook. Resolve release-blocking findings before exposing real customer data. Map applicable controls against OWASP ASVS; do not claim certification based on this guide.

08 · Customization as a product capability

The differentiator must be demonstrated through useful customer tasks, not the statement “more dynamic than Dynamics 365.” Measure setup time, upgrade safety, configuration reuse, and how often customers need code changes.

Level Customer/admin capability Proposed delivery
1 — Brand Logo, approved colors, company details, locale Pilot
2 — Workspace App navigation, labels, preferences, saved views Pilot
3 — Data/UI Typed custom fields, forms, sections, validation, dashboards Bounded pilot scope
4 — Process Triggers, conditions, approved actions, approvals Small action set in pilot; expand later
5 — Extension Custom entities, integration packages, custom apps Separate later release

Configuration lifecycle

Platform defaults → module defaults → tenant overlay → user preferences. Explicitly define which properties may be overridden and which layer wins. Keep stable internal keys even if visible labels change.

Every published configuration has a version, dependency list, author, timestamp, validation result, and rollback target. Use draft → validate → preview → publish. Publishing switches atomically; in-flight workflows keep a defined version. Distinguish rolling back presentation metadata from reversing a data migration, which may not be safe.

Pilot field types and constraints

Start with text, number/decimal, date, boolean, choice, and controlled lookup types. Define required/unique behavior, defaults, maximum lengths, search/export behavior, and field visibility. The server enforces the same schema as the renderer. Do not allow a new required field to silently invalidate existing records; require a backfill or explicit staged activation policy.

Upgrade-safe extension rules

Use namespaced immutable keys; archive instead of destructive removal when data or dependencies exist. Before publishing, identify referenced views, reports, workflows, and indexes. Preserve customer configuration during module upgrades and report conflicts instead of overwriting silently.

Do not accept raw SQL, arbitrary JavaScript, HTML scripts, or unlimited regular expressions from tenant settings. Use an allowlisted expression language with execution limits. Enforce quotas for fields, workflow depth, execution rate, and report complexity. Accessible contrast constraints still apply to customer-selected colors.

Pilot success demonstration: a tenant admin changes branding, adds a field, alters a form, saves a view, and publishes a bounded workflow without developer intervention; another tenant remains unaffected.

Proposed pilot scope

Workflow Minimum usable behavior
Customer workspace Signup/provisioning, invitation, membership, roles, app launcher
Customer information Shared accounts/parties, contacts, duplicate checks, relationship links
Lead management Capture, assign, qualify/disqualify, activity history, custom fields

Configuration Branding, selected custom fields/forms/views, role scopes
Reporting Pipeline totals, stage distribution, owner activity, filtered exports

End-to-end acceptance story

Create a tenant → invite a salesperson → assign the correct role → enable CRM → import or create a lead → record an activity → qualify the lead into appropriate account/contact/opportunity links → progress and close the opportunity → see authorized reporting → export permitted data.

Qualification must be transactional or have a clearly recoverable orchestration. Repeating the same conversion must not create duplicate parties or opportunities. Define duplicate policy for email/company data instead of silently merging unrelated records.

CRM and Sales boundary

The pilot includes sales-pipeline tracking within CRM. A separately sold Sales app can later add quoting, price lists, order management, approval rules, and downstream fulfillment. Agree the catalog boundary before selling both products so customers do not buy overlapping promises.

Intentionally bounded pilot

Use one chosen business segment, a small set of pipeline variations, and a clear migration/import path. Email synchronization, WhatsApp/telephony, marketing automation, advanced forecasting, offline mode, and AI recommendations are separately scoped integrations or later features.

Product evidence

Recruit 3–5 representative pilot businesses as a planning target, subject to owner availability. Observe users doing their own work, measure successful onboarding, lead-processing time, errors, and configuration difficulty. A demo with seeded records is not sufficient evidence of production usability.

Definition of done: core workflow tests and permissions pass; tenant configuration survives an upgrade rehearsal; a user can complete the selected workflow without developer intervention; support and recovery instructions exist.

10 · Later modules: bounded business contracts

ERP is a family of integrated capabilities, not one additional generic plug-in. Each module needs its own domain review, acceptance scope, migration plan, and independent-sale test.

Module First useful release Critical invariants / prerequisites
Sales Quotes, approved prices, discounts, orders Currency/rounding, approval authority, immutable accepted terms; no duplicate fulfillment
Inventory Products/SKUs, warehouses, receipts, issues, transfers, reservations Atomic stock movements; explicit negative-stock and valuation policies; unit conversions
Finance Chart of accounts, journals, receivables/payables, posting, period close, trial balance Balanced entries; immutable posted journals; controlled reversals; supported jurisdiction
HR Employee directory, organization structure, leave policy/requests Sensitive field access, correct accrual and approval, retention rules
Procurement Suppliers, requisitions, purchase orders, receiving Approval limits; receipt/invoice reconciliation; segregation of duties
Helpdesk Tickets, queues, ownership, SLA clocks, customer links Customer visibility, timezone-aware SLA timing, auditability

Scope distinctions

Invoicing is not full accounting. Generating an invoice PDF does not provide a general ledger, reconciliation, period controls, tax localization, or statutory reporting. Label the product accordingly until those capabilities exist.

HR records are not statutory payroll. Payroll needs country-specific calculations, benefits, deductions, effective dates, filing requirements, and qualified review. Exclude it from an HR MVP unless explicitly funded and scoped.

Inventory quantity is not inventory valuation. Choose FIFO, weighted average, or another supported method before posting cost of goods and financial integration. Test transfers, returns, adjustments, and backdated transactions.

Integration contract examples

An approved sales order requests a stock reservation through Inventory's service. A dispatched order emits an event; Finance creates an authorized posting using a stable source-document key. If an optional app is absent, the installed app still supports its promised standalone workflow and clearly communicates unavailable integrations.

Every extension phase begins with example business documents, state transitions, rejection cases, expected totals, and a named domain reviewer. Add jurisdiction-specific cases before claiming local accounting or payroll compliance.

11 · Workflows, reporting and integrations

Bounded workflow engine

Pilot triggers: record created/updated and scheduled reminder. Pilot conditions: typed comparisons over authorized fields. Pilot actions: create task, notify user, assign owner, and controlled field update. Add approvals only after defining authority, delegation, rejection, timeout, and resubmission semantics.

Use versioned workflow definitions, tenant-specific quotas, run history, correlation IDs, retry limits, exponential backoff, dead-letter handling, and a manual replay policy. Prevent cycles and repeated self-triggering. Execute with an explicit user or service identity; re-check membership, permissions, and entitlements before sensitive side effects. Snapshotting a workflow version is not permission to retain revoked authority.

Reporting

Begin with saved filtered lists, pipeline aggregations, dashboard cards, and CSV exports. Reuse the permission evaluator and field policy. Aggregate data can also leak sensitive information; permitted rows and fields must be applied before aggregation.

Bound report complexity, date ranges, page sizes, and export size. Use background jobs for large exports, short-lived private downloads, expiry, and audit events. Include tenant/policy/configuration versions in cache keys or invalidate caches when they change.

Integration boundary

Publish a versioned REST API and documented webhook events. Give each integration a tenant-scoped revocable credential and minimal scopes. Define pagination, rate limits, idempotency, retry semantics, and event version compatibility. Do not expose generic database access.

Store inbound provider event identifiers before applying effects; verify signatures and replay rules. Outbound delivery is at-least-once; consumers must deduplicate. Keep credentials in a secret store and redact payload fields from logs where needed.

Failure behavior

An email outage should not roll back a valid lead save. Record the business transaction and outbox entry, then retry notification. A failed financial posting needs visible reconciliation and cannot be represented as a successfully completed posting. Distinguish accepted-for-processing from completed operations in the API and UI.

Build versus buy: integrate commodity identity, payment processing, email, storage, and monitoring where economical. Own the tenant/module contracts, customization behavior, domain workflows, and user experience. Evaluate vendor export paths, regional support, costs, and failure modes in P0.

Proposed deployment path

Use a Linux container deployment if the future server supports it: reverse proxy/TLS → web/API → worker → PostgreSQL/Redis, with private object storage and external providers. Keep database and Redis ports off the public internet. Separate development, staging, and production credentials/data. A staging stack on the same host is logically separate but does not provide independent failure isolation.

Start with Docker Compose or equivalent reproducible orchestration. Kubernetes is not required for the proposed pilot. Pin images, run processes as non-root where practical, set resource limits, rotate logs, and document restart behavior. Build images in CI rather than editing production containers.

Provisional service objectives

Measure Initial target to validate
Typical CRUD API latency p95 ≤ 500 ms at 50 concurrent active virtual users
Representative data At least 10 tenants and 100,000 CRM records total, including one larger tenant
Load test error rate < 1% unexpected errors; zero isolation failures
Availability aspiration 99.5% monthly after measurement; not a contractual SLA

These targets are workload-specific, not server capacity claims. Record hardware, traffic mix, query distribution, dataset, and test duration with each result. A single server remains a single failure domain.

Operational controls

Use encrypted off-host backups, PostgreSQL WAL/PITR if adopting the one-hour RPO, and protected backup credentials. A daily dump alone cannot meet that target. Include object storage, configuration, encryption-key recovery, and identity-provider recovery in the plan. Rehearse restoration into a clean environment and measure the result.

Collect structured logs, request/job correlation IDs, latency/error metrics, queue lag, database saturation, disk use, backup age, and billing reconciliation failures. Configure actionable alerts and a named owner. Document restore, credential rotation, incident triage, migration failure, and rollback procedures before pilot launch.

13 · Master roadmap and planning assumptions

Proposed baseline, not a delivery commitment

Assume one experienced solution developer leading Codex, 30–35 focused project hours/week, timely product decisions, commodity integrations, and a deliberately limited CRM pilot. Team size, actual hours, budget, and target market remain open. Weeks start from approved P0 kickoff, not the PDF date.

P1 — Core vertical slice Weeks 3–6 Workspace → login → permission → lead → audit; G1
P2 — CRM alpha Weeks 7–10 Complete chosen CRM workflow and import/reporting; G2
P3 — Customization Weeks 11–14 Versioned fields/forms/views/branding and policy depth; G3
P4 — Commercial platform Weeks 15–18 Plans/entitlements/billing and bounded automation; G4

Planning envelope: 24 baseline weeks + 4–8 contingency = 28–32 weeks, approximately 6½–7½ months, for the scoped paid pilot. Baseline effort is roughly 720–840 focused hours, excluding contingency. First working slice targets week 6; CRM alpha targets week 10. These are phase forecasts, not promises.

How to keep the estimate honest

Measure completed, accepted work packages in the first four weeks. Re-estimate at each gate using observed throughput and remaining uncertainty. Reserve around one day per week for review, regression, documentation, and operations within the assumed hours. Do not count AI-generated code volume as completed work.

If availability is lower, use remaining effort ÷ actual weekly capacity as a starting recalculation, then account for integration delays. Do not assume doubling hours or agents halves elapsed time.

Critical path

Tenant/auth correctness → usable CRM workflow → versioned customization → entitlement/billing correctness → production evidence. Test and deploy incrementally throughout. Gates protect specific invariants; they do not prohibit a small experiment needed to validate the next phase.

14 · P0 and P1: define, then prove the core

P0 · Weeks 1–2 · Gate G0

Inputs: owner vision, future hosting/server inventory, pilot customer candidates, this guide.

Work packages

  • P0.1 Product contract: select segment, primary personas and three end-to-end workflows; write included/excluded scope and initial acceptance stories.
  • P0.2 Environment inventory: document OS, CPU/RAM/disk, services, domains, backups, network exposure, costs and staging options. Produce a proposed change plan.
  • P0.3 Technical spikes: prove OIDC session handling, membership resolution, RLS under pooling, a migration rehearsal, and one automated browser flow. Compare providers on supported requirements.
  • P0.4 Delivery setup: accept/reject ADRs; establish repository, issue/work-package template, CI plan, secrets approach, and dependency versions.

G0 evidence: approved scope and assumptions; spike results; reproducible environment instructions; no unresolved blocker to secure tenant-aware data access. Estimate is re-baselined with actual availability. Any spike code retained must meet production standards later.

P1 · Weeks 3–6 · Gate G1

Dependencies: G0 and selected stack/provider.

Work packages

  • P1.1 Foundation: web/API/worker skeleton, database migrations, health endpoints, basic CI, staging deployment and structured logs.
  • P1.2 Identity and tenancy: workspace provisioning, user membership/invitation, tenant switching, roles, tenant-scoped repository layer and RLS.

17 · Expansion roadmap and suite completion

After the CRM pilot, use observed demand and capacity to choose the next module. Do not start Finance and Inventory simultaneously by default when one person must review both.

Expansion Indicative incremental effort Exit gate
E1 — Sales + bounded Inventory 10–16 focused weeks Standalone order/stock workflows, concurrency and reconciliation pass
E2 — Finance foundation 16–28 focused weeks Scoped accounting reviewed by a qualified domain specialist; closing/reversal tests pass
E3 — HR core 8–14 focused weeks Employee access, leave/accrual and approvals pass; payroll excluded unless separately scoped
E4 — Procurement or Helpdesk 6–10 weeks per module Standalone value, dependency and cross-app workflow tests pass
E5 — Advanced configurability 12–24 weeks Custom-entity/extension lifecycle, migration safety, quotas and security verified

These are low-confidence ranges after a reusable core exists, not quoted estimates. Re-scope each phase with business examples, actual throughput, local requirements and maintenance load. Costs for support, domain review and production operations increase after launch.

Broad planning envelope

A scoped suite may take 18–30+ months from kickoff, depending on which modules and jurisdictions are included. This is a portfolio planning envelope, not the arithmetic sum of committed phases or a forecast of Dynamics 365 parity. Concurrent customer support can extend it substantially.

Module release checklist

  1. Define the catalog promise, included workflows and paid dependencies.
  2. Define owned entities, invariants, state transitions and integration events.
  3. Pass fresh-tenant standalone installation and onboarding.
  4. Pass upgrade, downgrade, archive/export and optional-app absence paths.
  5. Execute domain cases T33–T40 as applicable and add missing jurisdiction-specific tests.
  6. Execute security/entitlement regression for every new API, report, file and job surface.
  7. Reconcile integrated source documents to postings/stock movements; expose failures.
  8. Demonstrate production recovery and operational visibility for the new module.

Suite acceptance: every sold module meets its declared contract, and the promised combined workflows pass. Maintain a versioned capability catalog so “complete platform” has an explicit meaning at each release.

18 · Development pipeline and release discipline

One work package through production

Specify → implement → verify → review → stage → accept → release → observe. Keep work small enough to review within a day or two; split larger tasks by observable behavior rather than file count.

Stage Required output / check
Ready User story, scope, dependencies, test IDs, schema/API impact, completion criteria
Implement Bounded change, migrations, meaningful automated tests and updated docs
CI Formatting/lint, typecheck, unit/integration tests, build, dependency/secret checks
Review Tenant/access invariants, failure paths, domain correctness, migration/rollback strategy
Staging Same artifact intended for production; migration rehearsal; E2E and negative tests
Accept Owner UAT evidence and gate checklist; unresolved defects recorded
Release Backup/recovery point, compatible migration, health and business smoke checks
Observe Error rate, latency, queue lag, billing reconciliation and customer workflow checks

Database change discipline

Prefer expand → migrate/backfill → switch → contract. Keep old/new application versions compatible during deployment where necessary. Test on a staging copy or representative dataset. Estimate lock time and backfill cost. Never assume an application rollback reverses a database migration.

For destructive changes, define a separate migration plan, restore/roll-forward strategy, data validation and owner authorization. Delay column/table removal until compatibility and retention requirements are satisfied.

19 · Test strategy and execution rules

Shared test fixture

Create Tenant A and Tenant B with similar data and distinct record/file identifiers. Users: A-owner, A-manager, A-salesperson, A-readonly, B-owner, and a legitimate user with memberships in both tenants. Include a revoked member, an expired session, a restricted field, CRM-only entitlement, and expired/suspended entitlements. Use synthetic data and a real PostgreSQL instance for isolation tests.

Test layers

  • Unit/domain: calculations, state transitions, policy decisions, metadata validation, idempotency rules.
  • Integration: transactions, constraints, RLS and pooling, outbox, worker retries, billing reconciliation and migrations.
  • API/security: direct unauthorized requests, forged tenant IDs, field injection, report/export/file paths.
  • Browser E2E: onboarding, daily work, configuration and purchasing journeys.
  • Operational: load, restore, deployment, observability, failure/retry and incident response.
  • Human UAT: domain meaning, usability and task completion with representative customers.

Case notation

The next pages define T01–T48. Every case includes setup, action and expected result. G1–G5 identify the first relevant gate. E identifies later-module gates. Cases are release-blocking when their feature is sold or enabled. A genuinely excluded capability is marked N/A with a reason, never “passed.”

Keep a test execution ledger with: case ID, build, environment, fixture/version, executor/date, actual result, evidence link, defect reference and retest. Initial status for all cases is Not run. This document's PDF validation does not verify the future platform.

Failure classification

Tenant leaks, unauthorized changes, incorrect entitlement grants, duplicate financial/stock effects, data loss, and unusable recovery are release blockers. User-blocking defects in a promised primary workflow also block that workflow's release. Cosmetic issues may be deferred with a clear record and owner acceptance.

Coverage maintenance

The 48 cases are a foundation, not an exhaustive certification. Generate a route/job/report permission matrix as implementation grows. Add boundary-value, malformed-input, concurrency, regression, country-specific accounting, and accessibility cases from actual features and defects. Keep test assertions independent of the implementation's assumptions.

Principal risks and responses

Risk / signal Response
Core becomes an endless abstraction project Deliver the lead slice by P1; generalize proven patterns
“Dynamic” means unlimited everything Versioned capability levels, bounded expressions and explicit upgrade contracts
AI output outruns review capacity Small work packages, negative tests and evidence-based review
Accounting/payroll underestimated Narrow scope, country selection and qualified domain review
Billing/auth provider mismatch P0 proof and export/recovery review before deep integration
Single server failure or slow queries Measured capacity, off-host recovery, noisy-neighbor limits and later separation
Post-launch support consumes development time Budget support capacity and reforecast expansion

Budget model rather than invented prices

Monthly operating cost = compute + database/backups + object storage/egress + identity + email/SMS + monitoring + payment fees + AI development usage + support tools. Add one-time domain review, security review and migration/onboarding effort where needed. Obtain current provider quotes after region and workload decisions.

Commercial margin must also cover the owner's maintenance/support time, not only server rental. Define per-plan usage limits and observability before offering unlimited automation, storage, or AI features.

## Upload/dashboard slowness fix — 8 October 2026 (current release)

- **Owner report:** Admin panel very slow, especially upload actions; console showed `fbevents.js net::ERR_BLOCKED_BY_CLIENT` (ad blocker hiding the root-layout Facebook pixel — cosmetic, pre-existing, unrelated).
- **Diagnosis (read-only):** server healthy (~100 ms dashboard TTFB, DB 30–190 ms); the path from the owner's network is ~150 ms RTT with **HTTP/1.1 only** (nginx `listen 443 ssl` has no `http2`). Uploads move very large originals (receipt sample 10.9 MB) phone→VPS; server adds ~2.5 s/file (register + inline B2 PUT ~1.6 s + verifyFile). The big defect: after **every** upload, `refreshImages` re-downloaded `/api/images?nocache=1` = **2.05 MB JSON** (8,607 images + 8,607 signed thumbs) and re-parsed/re-rendered it on the device. Occasional Neon `fetch failed` (6 hits, stacks reference the OLD `.next-primary-v3` build) cause transient "Error reading content". Bundles unchanged by the assistant deploy (53→54 chunks, 1.7 MB) — chatbot not a factor.
- **Fix (chosen: fastest, zero content risk — additive only):**
  - `src/app/api/upload/local/route.ts` `result()` now includes `thumbnail: /api/media/<id>?w=400`.
  - `src/lib/uploadMedia.ts` `UploadResult` gains optional `thumbnail`.
  - `src/app/admin/dashboard/page.tsx`: `pendingUploads` ref + `media-backup-update` listener collects saved `{url, thumbnail}`; `refreshImages` prepends them locally and **skips the full fetch entirely** when a post-upload refresh has new items; falls back to the old `?nocache=1` full fetch only when there is nothing to append.
